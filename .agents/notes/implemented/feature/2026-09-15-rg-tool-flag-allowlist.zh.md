# 智能体笔记：rg 工具透传模型给出的 ripgrep 参数行

Status: implemented

[English](2026-09-15-rg-tool-flag-allowlist.md) | 中文

## 问题

文件系统检索套件暴露两个带类型参数的工具：`grep`(pattern、path、include)与 `glob`(pattern、root)。按 Codex 训练出来的模型会伸手去拿 ripgrep 自己的参数字汇——统计匹配数、只列出命中的文件、打印三行上下文、按类型过滤、反向匹配——而每一个要么需要翻译进带类型的 schema,要么是死路。`rg` 也不在智能体的 shell PATH 上:本包运行的二进制位于 `@vscode/ripgrep` 依赖内部,因此模型在 `bash` 或 `pwsh` 里敲 `rg` 得到的要么是另一个程序,要么什么都没有。

这个工具的第一版用白名单回应了这一缺口:交给打包二进制一个经过校验的 argv,并拒绝固定只读集合之外的所有参数——因为 ripgrep 会通过 `--pre` 执行其他程序、通过 `-f`/`--ignore-file` 读取任意文件,而这个 spawn 并不受限。

## 决策

`@deepseek-ai/dsh-tool-fs-search` 注册第三个面向模型的工具 `rg`。它只接受一个字符串参数,即 ripgrep 参数行;工具对它分词(按空白切分;单引号或双引号包裹一个 token;不做转义处理,不做展开,没有 shell),并把得到的 token 经与 `grep`/`glob` 相同的 `runRipgrep` 接缝交给打包二进制,同时前置 `--no-config`,使宿主配置文件无法贡献模型没有写下的参数。有两种形态会被直接拒绝,因为本工具永远无法满足它们:空参数行,以及位置参数 `-`(它要求 ripgrep 从本次 spawn 并不提供的 stdin 读取模式)。其余一切按原样交给 ripgrep,因此模型拿到的是 ripgrep 自己的参数字汇和 ripgrep 自己的参数错误。

白名单是被推迟,而不是被否决。这个 spawn 目前还没有经过沙箱接缝,因此会运行其他程序(`--pre`)或读取其他文件(`-f`、`--ignore-file`)的参数眼下是在那道围栏之外执行的;接入沙箱的部署可以选择在参数面重新引入边界,也可以交给围栏本身。

结果是 ripgrep 自己的 stdout,而不是结构化结果:模型要的就是 ripgrep 的输出形态,而检索卡片需要重新解析匹配,恰恰是本工具刻意不做的事。内联输出受新的 `rgMaxLines` 配置限制(默认 200),每行按 `grepMaxLineBytes` 预览;被截断的结果会把完整输出保存进 spill 存储并给出定位符,或者报告无法保存。工具不注册系统提示词段:可接受范围写在工具描述里,而「普通内容检索优先用结构化工具」仍归 `grep` 的提示词段负责。

## 曾考虑的替代方案

**保留只读白名单。** 在 spawn 受限之前它是更安全的默认值,但它也让这个工具变成了 ripgrep 的一个更小的方言:无害参数(`--sortr`、`--type-add`)一样被拒绝,模型无法用自己已知的 ripgrep 经验推断可用面,而且边界成立与否取决于白名单是否完整,而不是取决于某个执行点。推迟到沙箱落地。

**带类型参数的 `rg`。** 不予采纳:它复制 `grep` 的表面而不提供促成这个工具的参数字汇,还会触发跨文件重复检测闸门。

**把 `rg` 装进 shell PATH(modpack 的做法,也是 Codex 自己的做法)。** 在本仓库不予采纳:它需要仓库之外的二进制安装与用户 PATH 变更,并且会把检索整体移出工具层,失去内联上限、spill 交接与结果元数据。重新引入条件:某个交付部署若增加了二进制安装步骤,可以同时暴露 PATH 上的 `rg`,而不必移除本工具。

## 后果

模型无需 shell、无需安装步骤就获得了 ripgrep 的整套参数面,而工具的参数处理也从一个参数解析器加三张表,缩减为一个分词器。代价是明确的:在沙箱围栏覆盖到这次 spawn 之前,`rg` 可以运行预处理器、也可以读取模型点名的文件,因此挂载该工具的部署是在把自身进程的可达范围交给模型。

`tests/tools.spec.ts` 钉住分词(引号、空白、不做展开)、代表性参数形态的逐字 argv、两种拒绝、上限与 spill 路径,以及注册清单。
